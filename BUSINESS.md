# CRM для сети автомастерских (СТО)

Продуктовое описание бизнеса, воронки, ролей и экранов. Документ для согласования идеи и дальнейшей проработки прототипа.

---

## 1. Бизнес и ценность

**Бизнес:** сеть автосервисов (несколько филиалов СТО под одним брендом).

**Зачем CRM:** связать живые касания (звонок, визит, согласование, выдача) с деньгами (заказ-наряд → оплата) и командой (директор сети → руководитель филиала → рабочий), без абстрактных «лидов ради лидов».

**Ось правды:** **заказ-наряд (ЗН)**. Каждая работа оформляется нарядом. Деньги, статусы, ответственный мастер и конверсии считаются от ЗН и связанных касаний.

---

## 2. Живая воронка

Воронка — не sales-абстракция, а путь клиента по сущностям БД: касание → запись → визит → заказ-наряд → оплата → постсервис.

```
touches → appointments → visits (intake → diagnosis → approval → done_for_wo)
  → work_orders (created → assigned → [waiting_parts] → in_progress
                 → work_completed → ready_for_pickup → delivered → closed)
  → payments (+ tasks: постсервис / повтор)
```

Боковые исходы (не «успех» воронки): `touches.outcome` = rejected/spam; `appointments` = no_show/cancelled/rescheduled; `visits` = lost/cancelled (`approval_status` = rejected/thinking); `work_orders` = cancelled. Гарантия/рекламация — новый ЗН с `parent_work_order_id`.

### 2.1. Этапы подробно (как в БД)

Этапы ниже соответствуют enum’ам и таблицам (`touches`, `appointments`, `visits.stage` / `visits.status`, `work_orders.status`, `payments`, `tasks`). Согласование живёт на **визите**, не на ЗН.

| # | Этап (UI) | Сущность / код в БД | Что происходит | Кто трогает | Конверсия / деньги |
|---|-----------|---------------------|----------------|-------------|-------------------|
| 0 | Касание | `touches` (`channel`, `outcome`: recorded / callback / rejected / spam) | Звонок, WhatsApp, сайт, walk-in, рекомендация | Приёмщик / руководитель | **Касание → запись:** доля `outcome=recorded` (или с созданным `appointment`); отдельно % callback / rejected |
| 1 | Запись | `appointments.status`: new → confirmed → arrived \| no_show \| cancelled \| rescheduled | Слот, жалоба/услуга, авто, филиал; связь с `touch_id` | Приёмщик / руководитель | **Запись → визит:** % `arrived` + созданный `visit`; **no-show** = `no_show` / (new+confirmed+arrived+no_show); отмены и переносы — отдельно |
| 2 | Приёмка | `visits.stage=intake`; `status`: waiting_intake → accepted | Клиент на точке, авто принято (`accepted_at`) | Приёмщик / руководитель | **Запись → приёмка:** визиты с `appointment_id` / записи `arrived`; walk-in: визит без записи (вход сразу на #2) |
| 3 | Диагностика | `visits.stage=diagnosis`; `status=in_diagnosis`; поля `diagnosis_summary`, `estimate_amount` | Осмотр, дефектовка, предварительная смета | Мастер / приёмщик | **Приёмка → диагностика:** % accepted → in_diagnosis; средний `estimate_amount` |
| 4 | Согласование | `visits.stage=approval`; `status=pending_approval` → `approved`; `approval_status`: pending / thinking / approved / rejected | Клиент подтвердил объём/сумму (`approved_at`) или отказ (`lost` + `lost_reason`) | Приёмщик / руководитель | **Диагностика → согласование:** % `approval_status=approved`; % thinking (в ожидании); % rejected/lost + причины; upsell = повторное согласование допов |
| 5 | Визит готов к ЗН | `visits.stage=done_for_wo` (после approved) | Можно открывать один или несколько ЗН на визит (1 visit → N WO) | Руководитель | **Согласование → ЗН:** % approved-визитов с ≥1 `work_order`; число ЗН на визит |
| 6 | ЗН создан | `work_orders.status=created` | Позиции labor/part, суммы-кэш на шапке; исполнитель ещё не обязателен | Руководитель | Воронка ЗН: вход в pipeline; план работ / сумма `total_amount` |
| 7 | Назначен | `status=assigned` (`primary_assignee_id` / item `assignee_id`) | Руководитель передал наряд (или позиции) рабочему | Руководитель → рабочий | **Создан → назначен:** % и срок до назначения; загрузка мастеров |
| 7a | Ждём запчасть | `status=waiting_parts` (опциональный боковой) | Не искажает «в работе»; влияет на срок | Руководитель / рабочий | Доля ЗН в waiting_parts; среднее время в статусе |
| 8 | В работе | `status=in_progress` | Выполнение, доп. работы → снова согласование на визите/задаче | Рабочий / руководитель | Загрузка постов; срок в работе; просрочка (напр. >7 дней в in_progress/waiting_parts) |
| 9 | Работы завершены | `status=work_completed` | Мастера закончили по позициям | Рабочий | **В работе → завершён:** throughput мастеров |
| 10 | Готов к выдаче | `status=ready_for_pickup` (`ready_at`) | Авто ждёт клиента | Рабочий → приёмщик | **Готов, не забран:** ready_for_pickup / (ready+delivered+closed); задача `pickup` |
| 11 | Выдан | `status=delivered` (`delivered_at`) + `payments` | Клиент забрал; оплата полная/частичная/долг | Руководитель / касса | **Готов → выдан;** долг = `total_amount − Σ payments` |
| 12 | Закрыт (оплачен) | `status=closed` (`closed_at`) | ЗН закрыт по кассе; **факт выручки** в KPI | Руководитель | **Выдан → закрыт;** выручка = Σ `total_amount` (или labor) по `closed`; средний чек; маржа — для руководства |
| 13 | Постсервис | `tasks` (`remind_service`, callback, …) → новое `touch` / `appointment` | ТО, отзыв, гарантия, повторный визит | Приёмщик / система | **Повтор 30/90 дней:** доля closed с новым appointment/visit; LTV |

**Сводка конверсий воронки (для дашборда директора / руководителя):**

| Шаг | Формула (логика) | Зачем |
|-----|------------------|--------|
| Касание → запись | appointments с touch / touches (≠ spam) | Качество входящего |
| Запись → визит | visits по appointment / appointments (без cancelled) | Явка; рядом % no-show |
| Визит → согласование | visits `approval_status=approved` / визиты, дошедшие до diagnosis+ | Качество сметы / продажи |
| Согласование → ЗН | WO с visit_id / approved visits | Не теряем согласованных |
| ЗН → в работе | in_progress+ / created+assigned+… | Скорость старта |
| В работе → готов | ready_for_pickup+ / когда-либо in_progress | Срок ремонта |
| Готов → выдан | delivered+closed / ready+delivered+closed | «Висит на стоянке» |
| Выдан → закрыт | closed / delivered+closed | Сбор денег / дебиторка |
| Закрыт → повтор | повторный visit/appointment за 30/90 дн. / closed | Retention / LTV |

Отказы считать отдельно, не смешивать с «ещё в процессе»: lost/rejected после диагностики; cancelled на записи и ЗН; no_show.

### 2.2. Реальные кейсы (что учесть в воронке)

Ниже — типовые сценарии СТО. Их можно сократить или дополнить под прототип.

#### Вход в воронку

1. **Входящий звонок «шумит / не заводится»** — квалификация: марка, симптомы, срочность → запись или «приезжайте на диагностику».
2. **Walk-in** — клиент без записи; если есть свободный пост — визит сразу, иначе запись.
3. **Повторный клиент по напоминанию ТО** — лид из задачи «ТО через 10 тыс. км / 6 мес.»; короткая воронка (часто без длинной диагностики).
4. **Рекомендация / корпоративный клиент** (такси, автопарк) — отдельный тип клиента, договорные тарифы, отсрочка оплаты.
5. **Перевод с другого филиала сети** — запись создана на точке A, клиент едет на B; клиент общий, ЗН — у филиала выполнения.

#### Запись и визит

6. **No-show** — не приехал; задача «перезвонить», слот освобождается; метрика % no-show.
7. **Перенос записи** — клиент переносит день; история касаний сохраняется, этап не «сбрасывается в ноль».
8. **Опоздание / очередь** — визит есть, пост занят; статус «ожидает приёмки».

#### Диагностика и согласование

9. **Только диагностика** — клиент оплатил осмотр и уехал без ремонта (отказ от работ) — этап «отказ после диагностики», деньги за диагностику всё равно есть.
10. **Смета «нашли ещё»** — в процессе вскрытия доп. работы; повторное согласование (upsell), отдельное касание «звонок на согласование допов».
11. **Клиент думает** — смета отправлена, ждём решения; `approval_status=thinking`, задача callback; ЗН ещё не создан (или создан только после `approved`).
12. **Отказ от ремонта** — `visits.stage/status=lost`, `approval_status=rejected`, зафиксировать `lost_reason` (дорого / к дилеру / сам сделает).

#### Заказ-наряд и работы

13. **Один визит — несколько ЗН.** *Зафиксировано:* связь **1 visit → N work_orders** (например ЗН «подвеска» и ЗН «окраска» разным мастерам). Внутри каждого ЗН — позиции-работы (labor/part) со своими ценами; сумма ЗН = сумма позиций (кэш на шапке).
14. **Назначение руководителя** — руководитель филиала передаёт наряд (или позицию) конкретному рабочему.
15. **Переназначение** — рабочий заболел / перегруз; наряд другому.
16. **Ожидание запчасти** — статус «ждём запчасть», ЗН не «висит» в «в работе» без причины; влияет на срок и загрузку.
17. **Гарантийный ремонт** — отдельный тип ЗН: связь с исходным нарядом, без (или с частичной) оплатой клиента.
18. **Эвакуатор / не на ходу** — пометка срочности, другой слот/пост.

#### Выдача, деньги, после

19. **Частичная оплата / долг** — выдача с долгом; видно в кассе и карточке клиента.
20. **Безнал / юрлицо** — отсрочка, акт/счёт; для директора — дебиторка по филиалам.
21. **Клиент забрал без оплаты** (исключение) — контроль руководителя.
22. **Рекламация** — возврат после выдачи; новый ЗН типа «гарантия/рекламация», связь с исходным.
23. **Повтор через 2 недели** — «не помогло»; история в карточке авто критична.
24. **Напоминание ТО / сезонная замена шин** — исходящая задача → новая запись (закрытие петли retention).

#### Сетевые и командные

25. **Эскалация директору** — срыв сроков, конфликт, крупный чек, аномалия по филиалу.
26. **Сравнение филиалов** — одни и те же шаги конверсии из §2.1, разные %, где «сыпется» (запись→визит, согласование→ЗН, выдан→закрыт).
27. **Загрузка мастеров** — у рабочего слишком много открытых нарядов; руководитель видит очередь.

### 2.3. Что ещё можно учесть (бэклог, не обязательно в MVP)

- Канал лида (звонок / мессенджер / 2ГИС / реклама) и ROI канала.
- Нормочасы и выработка мастера (план/факт в часах, не только в ₽).
- Прайс/тарифы единые для сети + локальные исключения.
- Склад запчастей и резерв под ЗН (легко расползается — в MVP только «позиция в ЗН», без полноценного склада).
- Фото при приёмке/выдаче (состояние кузова).
- Согласование с клиентом в мессенджере со статусом «ожидает ответа».
- NPS / просьба о отзыве после выдачи.
- Страховые случаи / направления от страховщика (отдельный процесс).

### 2.4. Статусы сущностей (для UI) — актуальные enum’ы

**Касание (`touches`):** канал call / whatsapp / site / walk_in / referral / other; исход recorded / callback / rejected / spam.

**Запись (`appointments.status`):** new → confirmed → arrived | no_show | cancelled | rescheduled.

**Визит — этап (`visits.stage`):** intake → diagnosis → approval → done_for_wo | lost.

**Визит — статус (`visits.status`):** waiting_intake → accepted → in_diagnosis → pending_approval → approved | lost | cancelled.

**Согласование (`visits.approval_status`):** pending / thinking / approved / rejected.

**Заказ-наряд (`work_orders.status`):** created → assigned → [waiting_parts] → in_progress → work_completed → ready_for_pickup → delivered → closed | cancelled.  
Согласование **не** статус ЗН (оно на визите). Флаги: `is_warranty`, `parent_work_order_id`; долг = сумма ЗН − платежи.

**Позиция ЗН (`work_order_items.status`):** pending → assigned → waiting_parts → in_progress → done.

**Задача (`tasks`):** open → in_progress → done | cancelled; типы: callback, approve_extras, remind_service, pickup, escalation, other.

## 3. Роли и работа платформы

### 3.1. Директор сети (директор СТО)

**Видит:** все филиалы сети.

**Фокус:**
- план/факт выработки (выручка, нормочасы — по возможности) по сети и по каждому СТО;
- детальная информация по филиалу: воронка, касса, открытые ЗН, проблемные зоны;
- сравнение филиалов (конверсии, средний чек, долги, просроченные наряды);
- клиенты сети (сквозно), без необходимости вести каждый пост.

**Не делает в ежедневке:** назначение каждого наряда рабочему (это уровень филиала), если только эскалация.

### 3.2. Руководитель филиала

**Видит:** только свой филиал.

**Фокус:**
- наряды работ (создание, статусы, контроль сроков);
- клиенты филиала (и визиты «чужих» клиентов сети на свою точку);
- касса дня/периода (приход, долги);
- список работ / загрузка;
- **передача наряда одному из рабочих** на выполнение (назначение / переназначение);
- задачи приёмки и согласования.

### 3.3. Рабочий (мастер)

**Видит:** свои наряды, свои задачи, клиентов в контексте своих нарядов.

**Не видит:** финансы филиала и сети (выручка, маржа, касса, план/факт директора), чужие наряды (кроме случая, если руководитель явно не открыл — по умолчанию только свои).

**Делает:** берёт в работу, меняет статус выполнения, отмечает готовность, фиксирует комментарии / доп. находки (для согласования руководителем с клиентом).

### 3.4. Матрица доступа (кратко)

| Объект | Директор | Руководитель филиала | Рабочий |
|--------|----------|----------------------|---------|
| Дашборд сети | ✓ | — | — |
| Дашборд филиала | ✓ (любой) | ✓ (свой) | упрощённый: мои наряды/задачи |
| Клиенты | все | свой филиал (+ визиты к себе) | связанные со своими ЗН |
| Воронка / записи | все филиалы | свой | ограниченно / свои задачи |
| Заказ-наряды | все (просмотр) | свой филиал CRUD + назначение | свои: статус/комментарий |
| Касса / долги | все | свой | — |
| План/факт выработки | сеть + филиалы | свой филиал | свои нормы (опционально, без ₽) |
| Задачи | эскалации / обзор | свой филиал | свои |
| Назначение исполнителя | опционально | ✓ | — |

## 4. Минимальный каркас экранов

1. **Дашборд** (роль-зависимый)  
   - Директор: план/факт по сети, плитки филиалов, конверсии, выручка, долги, просроченные ЗН.  
   - Руководитель: касса дня, воронка филиала, открытые ЗН, загрузка, задачи.  
   - Рабочий: мои наряды сегодня, задачи, что «готово к сдаче».

2. **Клиенты** — список (поиск, фильтры) → **карточка клиента**  
   Автомобили, история визитов/ЗН, касания (звонки), долги (для руководства), задачи.

3. **Воронка / сделки** — канбан или список по этапам из §2.1  
   (запись → визит/согласование → ЗН created…ready → выдача/закрытие → постсервис), фильтр по филиалу (у директора).

4. **Заказ-наряд** — карточка: авто, клиент, позиции работ, исполнитель(и), статусы, сумма (сумму рабочему не показывать или только объём работ без денег — продуктово: **рабочему без финансов**).

5. **Задачи и напоминания** — перезвонить, согласовать, ТО, забрать авто, эскалации.

6. **Переключатель роли** (для прототипа) — директор / руководитель СТО / рабочий, чтобы показать разный UX на одних данных.

Опционально в том же каркасе: список филиалов (директор), «касса» как вкладка дашборда руководителя.

## 5. Сущности (черновик модели)

- **Филиал (СТО)** — точка сети.  
- **Пользователь** — роль + привязка к филиалу (директор — ко всем).  
- **Клиент** — человек / организация.  
- **Автомобиль** — госномер, VIN, марка/модель, пробег; принадлежит клиенту.  
- **Касание** — звонок, сообщение, визит; связь с клиентом/авто.  
- **Запись** — слот, филиал, услуга/жалоба.  
- **Заказ-наряд** — филиал, авто, клиент, статус, суммы, сроки.  
- **Работа (позиция ЗН)** — наименование, исполнитель, статус; *наряд на работу = ЗН или позиция — зафиксировать в прототипе.*  
- **Платёж / касса** — привязка к ЗН, филиал, тип оплаты.  
- **Задача** — тип, срок, ответственный, связь с клиентом/ЗН.  
- **Тариф / прайс** (упрощённо) — справочник работ для подстановки в ЗН.

Связи: Клиент 1—N Авто; Авто 1—N ЗН; ЗН 1—N Работы; ЗН 1—N Платежи; Филиал 1—N ЗН; Пользователь N—1 Филиал (кроме директора).

## 6. Метрики: живые деньги и конверсии

Считать по цепочке сущностей из §2.1 (не по абстрактным «сделкам»). Факт выручки в текущем прототипе — ЗН в статусе **`closed`**.

**Директор / руководитель:**
- Выручка план/факт (день / неделя / месяц): Σ по `closed` (в UI сейчас акцент на labor / `total_labor_amount`).
- Pipeline: Σ по ЗН в статусах created…delivered (ещё не closed).
- Средний чек по `closed`.
- Конверсии воронки (см. таблицу в §2.1): касание→запись, запись→визит (+ no-show), визит→согласование, согласование→ЗН, ЗН→в работе, в работе→готов, готов→выдан, выдан→закрыт, закрыт→повтор 30/90.
- Доля отказов: `visits` lost / `approval_status=rejected` + `lost_reason`; `work_orders.cancelled`.
- Просроченные ЗН: in_progress / waiting_parts дольше N дней (в прототипе N=7).
- Долги: delivered (и др. незакрытые) с `total_amount > Σ payments`.
- Загрузка: открытые ЗН на филиал / на `primary_assignee_id` (и по позициям).
- Доля waiting_parts и «готов, не забран» (ready_for_pickup).

**Рабочему не показываем** денежные агрегаты сети/филиала; достаточно количества и статусов своих нарядов.

Избегать в MVP: vanity-метрики без денег («активность», «количество кликов»).

## 7. На что ещё обратить внимание

### Продукт и границы MVP
- Не тащить склад, бухгалтерию, 1С, зарплату в первый контур — иначе размоется история «живой воронки и денег».
- **1 визит → N заказ-нарядов** (фиксировано в `ARCHITECTURE.md` §11): разные мастера/зоны = разные ЗН; позиции внутри ЗН для состава и цен.
- Клиент сети может обслуживаться на разных филиалах — карточка клиента сквозная, ЗН всегда с `branch_id`.

### Операционка СТО
- Госномер / VIN — главный ключ поиска, не только ФИО.
- Согласование допов — отдельное касание и часто отдельная задача; иначе «потерянные» деньги и конфликты.
- Статус «ждём запчасть» обязателен — иначе искажается «в работе» и план/факт сроков.
- No-show и отказ после диагностики — полноценные исходы воронки, не мусор.

### Роли и доверие
- Финансы — только директор и руководитель филиала; рабочий работает с нарядами и задачами.
- Назначение исполнителя — право руководителя (ключевой сценарий передачи наряда).
- В прототипе переключатель ролей должен реально менять данные на экране, а не только подпись.

### UX для теста
- Дашборд с ₽ и конверсиями на первом экране — сразу видно «не абстрактный CRM».
- Карточка клиента = история жизни авто, не пустой профиль.
- Канбан воронки подписать этапами СТО, не «Lead / Won».

### Риски
- Слишком много статусов → упростить до понятного набора (см. п. 2.4).
- Путаница «сделка» vs «заказ-наряд» → в UI лучше «Заказ-наряды» / «Воронка сервиса».
- Директор без детализации филиала и руководитель без кассы — слабая демо-история; оба слоя нужны.

### Что показать в истории работы с ИИ (для тестового)
- Как выбрали нишу и воронку.
- Как зафиксировали роли и матрицу доступа.
- Где сознательно обрезали scope (склад и т.д.).
- Итерации: кейсы воронки → экраны → модель данных.

## 8. Короткий pitch

CRM для сети автосервисов: воронка по сущностям БД «touch → appointment → visit (intake/diagnosis/approval) → work_order (created…closed) → payment → task/повтор», деньги и конверсии по филиалам, роли директор сети / руководитель СТО / рабочий с назначением нарядов. Не абстрактный sales CRM, а операционный контур мастерской.
